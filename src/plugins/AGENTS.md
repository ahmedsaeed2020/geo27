## src/plugins rules
- Digit apps are plugin manifests in src/plugins/<app>/ registered in src/plugins/registry.ts; src/plugins/runtime.ts overlays them on catalog meta (catalog.ts calls overlayMeta/pluginMeta) and never edits core files, so disabling a plugin restores the Original exactly.
- Plugin behaviour is declarative (expr.ts conditions); manifest `script` strings are only written into the Frappe export (src/plugins/export.ts, validated by scripts/validate_frappe_app.py), never executed in the browser.
- Desk customizations (Custom Field, Property Setter, custom DocType, Server/Client Script, Workflow records) are composed into a live `site_customizations` manifest by liveManifest() in src/plugins/runtime.ts, so they apply instantly through the same overlay and export path as plugins.
- Virtual API reads/writes pass session.ts assertPerm via cachedMeta (fail-closed for non-admin when meta is unknown), so plugin data access enforces role and User Permission rules at the data boundary.
- Apps declare actions (virtual declarative effect or server stub), settings, department_sections, frontend and compatibility in the manifest, and their menu is derived from it; src/plugins/appShell.ts keeps the active app for the session and src/components/Shell.tsx renders its nav (ActiveAppNav), so app navigation stays inside the app shell without new routes.
- src/plugins/appPackage.ts exports owned frontend sources as a candidate bundle plus digit/integration.json marked SERVER_OR_STAGING_REQUIRED and server API stubs that raise until implemented, so an export never claims a working Frappe frontend or controller.
- Client Script records are parsed declaratively by clientScriptParser.ts (never executed), so refresh/field-change/button/set_query behave without eval.
- App experience slots (experienceSlots.tsx, one line per app in slotRegistry.ts) are the only way app UI (sidebar, breadcrumbs, form panels, grid keys, dock, workspace extras) enters Core screens, gated on app enabled AND experience active so disabling restores the Standard Desk; app styles live in an app-owned stylesheet scoped to the theme class (e.g. digit_pro/digit_pro.css) linked from __root, so Standard Desk CSS never changes.
- `default_enabled` apps are enabled once per clean browser by __root applyEntryParams; afterwards Apps & Plugins keeps the choice.
- Behaviour an imported app needs from engine hooks the Final Core lacks lives in the app's own compat/ folder (e.g. digit_hr/compat: identity-narrowed scope/session, workflow pre-validation, Core-draft helpers) and the remaining native-path gaps are listed as blockers, so protected engines change only by owner approval.
- The full DIGIT CRM sample corpus is generated only inside digit_crm/demoPreview.worker.ts (its own adapter memory; no browser storage) and read page by page through demoPreviewIndex.ts; demoGenerator.ts stays free of UI/runtime imports, so samples never enter the shared store.
- DIGIT FSM's information architecture (nine rail groups → contextual workspace destinations FSM_DESTINATIONS with Overview/Work/Documents/Reports/Details tabs, N-screens kept as non-featured deep links, separate technician and portal-preview hubs, workspace switcher emphasis) derives only from src/plugins/digit_fsm/screens.ts, visit facts (lead technician via Lead booking → FSM Technician → Employee) only from domain/visits.ts, and docs/digit_fsm CSVs are regenerated from live source by scripts/fsm-docs.ts, so menu, group workspaces and documentation never drift.
- DIGIT FSM destination overviews come only from ui/ov specs (OVERVIEWS keyed by destination, PAGE_OVERVIEWS for dedicated pages) drawn with the ui/insights.tsx kit and hosted as blocks of the shared Dashboard Designer by OverviewFrame, where every panel states its source, formula, filters, permission note and drill and missing sources render as "Source unavailable", so analytics stay traceable and nothing is invented.
- A DIGIT FSM KPI with a canonical home screen sets `KpiDef.screens` (analytics/kpis.ts); scripts/fsm-docs.ts lists it only there, never on every screen sharing its source report, so KPI identifiers keep one mapping.
- All 20 DIGIT Pro section workspaces render exactly three tabs (Dashboard · Documents & work · Full reports) from the one SectionWorkspace renderer (owner 2026-11-09), re-homing every earlier five-tab panel; legacy ?tab=work|details are redirected in the route beforeLoad, and only RUN11_SLICE workspaces (run11.ts) carry PLACEMENTS_448 ids on data-run11-placement until their placements are mapped, so one renderer serves every workspace and nothing is hidden with CSS.
- DIGIT Pro section workspaces render the Core Document Hub from src/plugins/digit_pro/hubs.ts (workspace navigation + native Workspace cards + department setup + RELATED_PLACEMENTS from PLACEMENTS_448 DOCUMENT rows) through ProHub.tsx, with hub state in hub_* section URL keys, and their Overview through the Core Dashboard Designer with contracts from proDashboards.tsx whose default layout is the original composition, so documents and dashboards stay source-traced and un-customized pages look unchanged.
- DIGIT Pro review samples (src/plugins/digit_pro/sampleVolume.ts, registered in digit_pro/boot.ts) join the memory-only sample layer with explicit names and visit-relative dates, so date-relative Pro figures stay populated without changing stored data or the Pro stock-reconciliation evidence (posting.ts still does not maintain Bin).
- Shared-experience contract v1 (src/plugins/experience/: contract.ts zod schema, registry.ts, mount.ts) is declared one line per app in src/plugins/experienceRegistry.ts on top of the plugin registry: strict validation rejects unknown keys, other versions, duplicates, unknown plugins and adapters/blocks not owned by the declaring app; discovery fails closed (NOT_REGISTERED / NOT_INSTALLED / PERMISSION_DENIED / INCOMPATIBLE), Frappe-host-only apps (Distribution) stay declared but NOT_INSTALLED, and `server:` owners are labels that resolve CONTRACT_NOT_READY, so the preview never exposes an app or figure it cannot back. Registers list `ids` only from app source or an imported owner catalog, with optional per-id evidence `statuses` (UNMATCHED_SOURCE_REQUIRED ids are reported as blocked, never force-mapped), and each app derives screen `featureIds` and screen `kind` (WORKSPACE/GLOBAL/PROFILE/CONTEXTUAL_ACTION/MOBILE_ROUTE) from its own tables (registry.ts featureCoverage reports unlinked/blocked/unknown ids), so coverage stays traceable and never hand-maintained.
- The shared Shell's one content host `<main data-shell-main>` names the registered screen of the current path (experience/screenHost.ts → registry.ts screenAtPath, literal routes over templates), so route → registered screen → rendered host is read from the live page; never add a second content host.
- Enterprise host overlay behaviours (digit_enterprise public/js pro-sections.js, con-screens.js) are listed once in experience/legacyPatches.ts as SOURCE_OWNED / MIGRATED / KEEP_SERVER / KEEP_HOST with replacement, test and host retire guard keyed to source DOM contract markers (data-dp-tab-contract, data-dp-reports-contract), so host patches are retired by evidence and the host snapshot is never edited here.
- DIGIT Pro Run11.1 ids come only from docs/run11_1/source CSV copies via scripts/pro-run11-catalog.py → digit_pro/run11Catalog.generated.json (status from the docs/run11_1 matrices and the latest BROWSER_EVIDENCE receipt), so no id is invented, given its own screen, or upgraded without evidence.
- Shared blocks render only through components/experience/ExperienceBlocks.tsx placed once by the host app; figures and display labels come from the owning app's adapter (its own scoped reader), and each app+screen+block claims one mount, so a block never stacks and the Core never computes app figures.
- Dedicated app pages are registered screens only when the app's own source names them (Pro nav.ts via proNavPages, HR HR_PAGES, Construction R19 `historical` via R19_PAGE_SCREENS); routes no source names stay unregistered and are listed, so a page's identity is never guessed.
- An app places shared Core pages through its experience slot `corePage` (places / Eyebrow / Tabs; DIGIT Pro: digit_pro/CorePagePlacement.tsx reading nav.ts, sub-links via sectionCorePages), resolved by experienceSlots.ts corePageOwner, so one nav manifest decides where a Core page lives.
- Apps add permission-level rows to other apps' DocTypes only through manifest `docperms` (overlayMeta appends them to a copy; the export applies them after migrate with frappe.permissions.add_permission), so disabling the app restores the native permissions.
- DIGIT Pro finance home figures (P&L split, monthly bank/cash flow, bank vs books, month expenses) come only from digit_pro/financeHome.ts over scoped native records (P&L basis = dash92 plFigures, bank side = the native Bank Reconciliation Statement runner) with a drill per figure, and digit_pro/FinanceCards.tsx places them on /pro/dashboard and /pro/accounting, so card, list and report always show one number.
- `registry.ts` exposes the built-in apps through `builtinPlugins()`, read at call time, because plugins import the adapter and adapter → catalog → runtime → registry is an import loop; a list built at load time breaks server rendering.
- DIGIT FSM money and field facts come from one place each: domain/billing.ts (partsFlow, hoursOf, vanStock, jobBilling equation), domain/field.ts (myDay, workPack), domain/offline.ts (capture/sync/conflict) and domain/portal.ts (grant scope); screens, queues, reports and the draft-invoice hand-off read them, so figures never diverge between pages.
