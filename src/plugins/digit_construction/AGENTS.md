## digit_construction rules
- Read models live in domain/data.ts and domain/schedule.ts and compute from adapter records at render time; reports.ts and every page call them, so cards, reports and screens show one number (reconciled by reconcile.test.ts).
- Costing is purchase basis: open PO lines (net − billed) and unbilled active work-order lines are commitments; submitted Purchase Invoice items and Journal Entry expense lines are actuals; receipts, returns and stock issues are never cost events, so commitment and cost are never double counted.
- Writes go through domain/services.ts (idempotent Create From, policy-gated finals), workflows.ts + src/lib/workflow.ts, domain/hooks.ts (adapter hooks) and native posting.ts; nothing here writes GL Entry or Stock Ledger Entry, so ledgers stay Core-owned.
- Undefined owner policies (P1–P9, Digit Policy Decision) block only the dependent final action via policyDefined/PolicyGate; drafts and calculations stay usable, so no policy is silently assumed.
- The owner rulings P1–P9 live in seed.ts POLICY_RULINGS (insert-if-missing + one-time upgrade of untouched records) and ownerDecisions.ts; their Finance values (P2 account, P5 tolerances/cap, P7 Digit Expense Account mapping) are never seeded, and an empty value applies the ruled fallback (P2 release stays a draft, P5 report only, P7 no journal), so no Finance value is invented.
- Schedule rules port the source domain/schedule.ts (calendar days inclusive, successors move later only, root excluded, no critical path); rescheduling writes native Task dates only through documentApi.updateDocument all-or-nothing after a preview, so permissions and hooks always apply.
- Project 360 tabs follow the source projects.tabGroups (8 groups); legacy ?tab=commercial / ?tab=subcontracts stay as aliases, so old deep links keep working.
- docs/digit-app-builder/construction/DOCTYPES_FIELDS_RELATIONS.md is generated by `bun scripts/construction-schema-doc.ts` from the manifest; regenerate it after schema edits instead of hand-editing.
- Demo fixtures are insert-if-missing with explicit names (seed.ts) and skip user-edited records, so reinstalling never overwrites user data.
- Every report, portfolio and project picker scopes projects with domain/queues constructionProjects (contract type or linked construction record, session-scoped); project-required reports run only for an explicitly selected readable project with filters in the URL, so no non-construction or silently chosen project appears.
- Figure drill-downs open the same rows the read model sums (Project Cost Sources = costSources = costBuckets), so a tile and its drill total always match.
- Demo records keep unset child tables as [] and lose only rows byte-identical to the preview generator (domain/demoTables.ts, run from boot and after install), so opening a demo form never adds sample rows to demo data.
- WBS (domain/wbs.ts) and BOQ comparison (domain/boq.ts) are read-only views over existing records; BOQ amounts use the same lineAmount as the BOQ hook, so the comparison equals each BOQ total.
- A submitted Digit Cost Allocation re-attributes exactly one unmapped / out-of-budget source row to an approved budget line inside costBuckets (data.ts activeAllocations); the source document is never edited and cancelling the allocation restores the original attribution, so cost figures stay traceable to source rows.
- The cost source verifier read model (domain/costVerify.ts) never imports posting.ts (manifest → reports graph); allocation/review writes live in domain/costActions.ts and go through documentApi (permission, naming, hooks, submit).
- Procurement plan and material position (domain/procPlan.ts) follow native child-row references only (material_request_item, purchase_order_item, po_detail) and keep ordered / received / issued valuation / invoiced cost as separate measures that each drill to the rows they sum, so no procurement value is double counted or merged into one actual.
- Cash flow (domain/cashflow.ts) attributes each payment reference through its invoice's project and keeps overdue, later and undated lines out of the projected closing; advance / retention schedules (domain/advances.ts) reconcile to contractPosition and treat contract terms as terms, never as ledger balances, so cash and retention figures match the financial position page.
- Saved report views and dashboard layouts are owner-only records (Digit Saved View, Digit Dashboard Layout) written only through domain/layoutActions.ts and resolved by domain/layouts.ts (personal → role → company → system; stale ids ignored, new items appended visible), so personalisation never changes a figure or another user's screen.
- Controlled print copies (Digit Print Artifact) are written only by domain/printActions.ts and validated by checkArtifact (immutable lineage, void with reason, no delete); templates live in domain/print.ts and are the manifest print_formats, so preview, issued snapshot and Frappe export use one markup.
- Construction settings are edited only through domain/settingsAdmin.ts saveSettings (revision check, shared validation hook); settings without verified metadata are listed as gaps, never added as fields.
- Project team memberships live only in the Project custom table digit_team; domain/teamModel.ts owns the read model and row rules (also the Project hook) and domain/team.ts the revision-checked writes (re-exporting the model), so reports import teamModel without pulling documentApi into the manifest graph and Project 360, the native form and the team screen never diverge.
- R19 workspaces (r19/: generated source/contract JSON from scripts/construction-r19-import.py, workspaces/metrics/visuals read models, samples.ts demo rows, reportCrosswalk.ts dispositions) render through ui/r19Workspace.tsx on the shared Dashboard Designer and Document Hub with exactly three tabs; docs/digit-app-builder/construction/r19/ traces are regenerated by `bun scripts/construction-r19-docs.ts`, so a figure without a source shows as unavailable rather than invented.
- Company isolation is data-driven: every project-linked app DocType carries the project's company (schema withCompany + domain/companyScope.ts hook), so Company User Permissions scope app records like native ones; never add a per-screen company filter as a substitute.
- The 95/164/55/73 contract crosswalk is data in crosswalk.ts (one disposition per contract ID, refs checked against manifest, catalog and exports) and docs/.../CROSSWALK_95.md is generated by `bun run ./scripts/construction-crosswalk.ts`; update the table when a screen/report changes and regenerate, because crosswalk.test.ts fails on a stale or unresolved entry.
- Approval steps are the workflow states with a decision transition (reportsGap.ts DECISIONS: Approve, Reject, Return, Certify, Review); operating, negotiation and rework states are not approvals, so aging never counts an active contract as waiting.
- Linked records the session user may not read are never shown (no link, name or code): screens resolve them through domain/access.ts canSeeRecord (DocType role permission, plus on the Frappe host the server-delivered permitted record set from boot `delivered`) and render the bilingual Restricted marker, so the UI never widens Frappe's own read permissions.
- domain/host.ts says where the screens run (virtual preview vs Frappe host); browser-only demo / maintenance writes and success notices before server acceptance are disabled on the Frappe host, so the server stays the only writer there.
- Owner test-list department rules live in domain/<dept>.ts (mgt.ts, site.ts, tendering.ts, …) as pure (doc, before) rules registered in hooks.ts, with a same-message Python twin in rules/<dept>.py and reports in reports<Dept>.ts; testlist/dNN.test.ts checks each row on a real save and against both twins (testlist/twin.ts), so a rule is PASS only when browser and server agree.
- Optional numeric settings and row amounts treat 0 as blank in both twins (e.g. tendering.ts setting / rules/tendering.py), because Frappe stores an empty Percent / Currency / Float as 0.
- The server-twin harness (testlist/twin.ts) also compares cascades: a successful case runs the hook's after on the live store, reads back the records it created or changed and undoes them, so browser and Python follow-on writes must match too.
- Department 04 commercial rules (change pricing requests, commercial claims, time extensions, bundling events into variations, budget revision from an approved variation, prospective terms) live in domain/commercial.ts with the twin rules/commercial.py; change-event stages come only from domain/changes.ts (eventStage for events, stageOf for lines), so reports and exposure cards share one stage model.
- Department 05 subcontracting rules (compliance status and the activation guard, line lock, subcontract changes, back charges deducted once, delay penalty, measurement evidence, subcontract final account, subcontract retention release) live in domain/subcontract.ts with the twin rules/subcontract.py; an approved subcontract final account closes the work order and zeroes its open commitment in costSourceRows, so cost figures follow the closure.
- Department 06 cost-control rules live in domain/costControl.ts with the twin rules/cost_control.py (codes, pay-item links, allocation splits, forecast promotion/chain, attribution snapshot, follow-up SLAs, approval cap); a retired or unknown cost code on a budget or Purchase Order blocks, budget lines are cost code × category (control.ts budgetKey, data.ts sourceFitsLine), and the budget limit comes only from control.ts blockTolerance reading the Finance settings budget_block_pct / budget_grace_months (empty = warning only), so no limit or grace period is hard-coded.
- Subcontract Purchase Invoices carry the gross certified value per cost code with retention / advance recovery as purchase "Deduct" tax rows (services.ts createPurchaseInvoice, native posting.ts), so cost is gross, retention stays a payable and the payable total is unchanged.
- Owner test-list results (docs/construction/TEST_RESULTS.csv, TEST_SUMMARY.md, FUNCTION_CATALOG.md) are generated only by scripts/construction-test-results.py from docs/construction/testrun/*.json written by the testlist suites, so no row is PASS without a passing test.
- Department 07 procurement and stores rules live in domain/supply.ts with the twin rules/supply.py (over-receipt, claim gap, issue cost code, movement reason, PO approval level / author / zero price, RFQ cancel reason, issue requests) and apply only to construction-project rows (isConstructionProject), so other apps' purchasing is untouched; reads in services that a role check already gates use asSystem.
- Department 08 resources rules live in domain/resourcing.ts with the twin rules/resourcing.py (usage one-per-day + fuel, attendance induction note / active employees / no cross-project overlap per shift, booking activation by PM/DIR not the author, permit issue, expense receipt, owned-machine serial) and reports in reportsRes.ts behind role gates (DEC-259 / 279 / 280), so resource figures stay indicators that never post.
- Department 09 finance and closeout rules live in domain/finance.ts with the twin rules/finance.py (invoice approval level without a PO, payment hold / over-allocation / compliance warning, PO budget override log, WIP adjustment one per period with posting off until the revenue basis is ruled, commissioning witness / certificate / defect, handover asset completeness / review / return task, project close gate) and reports in reportsFin.ts; earned value, WIP and Actuals vs GL read costPosition / contractPosition / GL Entry and never post, so finance figures stay traceable to native ledgers.
- Visible addresses are /construction/<department>/<workspace>/<tab> and /construction/doc/<doctype>/<name>: urls.ts conInput/conOutput is the router rewrite (src/lib/appUrls.ts) and shell links written outside the router use publicHref, so no /plugins/… address is ever shown while the code stays in this folder.
- The Frappe section contract (contract.py, CONTRACT_VERSION 3: 36 section keys with documents, reports, KPI slots, queues, roles) is generated from generator/contract.ts over r19 workspaces + metrics; Enterprise renders only from it, so no Construction content is hard-coded in Enterprise.
- Native-form extras (service buttons, non-blocking budget / payment notices) enter only through the FormPanels slot (ui/formNotices.tsx) and write through domain/services.ts, so forms, fields and posting stay unchanged.
- App access comes from the app's role list (slots.tsx enterprise.roles, owner ruling DEC-015): Desk User is never granted automatically and a user without an app role sees only Home.
- The owner work-list result (docs/construction/ent36/DIGIT_CON_ENT_WORK_LIST_RESULT.csv + ENTERPRISE_36X3_SUMMARY.md) is generated by ent36/results.ts from ent36/worklist.ts classify over live source and checked by ent36worklist.test.ts (ENT36_WRITE=1 rewrites), so a row is never marked done without the code it names.
- Department dashboards are data in r19/deptDashboards.ts (the prototype composition: KPIs, chosen charts from r19/visuals.ts DEPT_VISUALS, insights, decisions, the four workspaces) rendered by ui/r19Workspace.tsx on the shared Dashboard Designer, and chart labels go through its localize() (Arabic project titles on Arabic screens), so a department page never gets its own chart code.
- Form rules-while-typing read the same adapter hooks as the save (hooks.ts hasHook/computeDoc) plus the generated prototype guide ux/docGuide.generated.json filtered to DocTypes that exist, so the panel shows the save's exact refusal and never names a missing document.
- Construction go-live steps and master-data checks enter the shared setup guide only through setupProvider.ts registerSetupProvider (src/lib/coreShared/setupGuide.ts), so the Enterprise guide stays one page for every app.
- The UX depth checklist result (docs/construction/ux/DIGIT_CON_UX_DEPTH_CHECKLIST_RESULT.csv + UX_DEPTH_SUMMARY.md) is generated by ux/uxDepth.ts from the screenshot run receipts (screens/shots.json, journeys.json) via `UXD_WRITE=1 bunx vitest run src/plugins/digit_construction/ux/uxDepthResult.test.ts`; a row is BLOCKED when its shot has errors, overflow or a blank page, so the result never claims a screen nobody opened.
- The rich demo company (volume.ts + demoPortfolio.ts) is created only through the document rules (computeDoc, workflows, posting for submitted vouchers), insert-if-missing with explicit names and removable through demoControl.ts, so every figure drills to real documents and reloading never duplicates.
- The research evaluation result (docs/construction/round_data_print/DIGIT_CON_RESEARCH_EVAL_RESULT.csv + ROUND_SUMMARY.md) is generated by ux/researchEval.ts (targets in researchEvalMap.ts, printable list in ux/printList.ts) from the screenshot and journey receipts in research/shots.json and journeys.json (RDE_WRITE=1); researchEvalResult.test.ts fails on a stale CSV, so a score is never hand-edited.
- Stage bars and requirement cards use the Enterprise kit (DistributionBar, RequirementCards) fed by read models that reuse the rule checks (data.ts claimStages, finance.ts closeoutRequirements = closeGateErrors, subcontract.ts prequalRequirements = p8Missing), so a card never disagrees with the save refusal.
- Offer comparison boards (ui/compare.tsx) draw domain/quoteBoard.ts read models with the Enterprise kit ComparisonColumns; awards go only through services createPurchaseOrderFromQuotation / awardQuotationLines or the Bid Leveling Award transition, so a board never prices or awards by itself.
- Approval-request pages (ui/decision.tsx) read domain/changePage.ts (Version moves, Workflow and user comments, decision fields, linked documents) through the kit DecisionLayout / DecisionTimeline / ImpactCards; demoPending.ts dates unedited demo documents' pending step 2–5 days before today as a marked Version + Workflow log (approval averages ignore marks), so path, timeline and aging report show one waiting time.
- Construction rules skip demo records while they are seeded and posted but run for a workflow decision taken on one (hooks.ts registerDocHook), so reasons, no self-approval and follow-ups (e.g. the award's work order) apply to demo documents too.
- Resource boards (crew week + labour budget line, equipment load by day, the site day hour by hour) are read models in domain/boards.ts drawn with the Enterprise kit ResourceBoard; labour cost uses the classification Labor Rate when a row has one (the laborCost basis) else the crew member planned daily cost ÷ the standard day, costs show only to seesRates roles, and equipment load uses the Utilisation card basis, so a board never invents a rate or a figure the cards do not share.
- Approval, payment and payout of claims, certificates, subcontract bills and change orders come only from domain/payStates.ts (meaning, not the raw workflow state) and render through ui/payColumns.tsx on the hub; a change request is a Workflow comment + a task for the preparer, so the three status columns never share a value.
- Stage boards (domain/stages.ts → ui/stageBoards.tsx on the Enterprise StageBoard) move tenders only through kanbanBoard.moveCards and change events only through a workflow transition; stages no manual action reaches are ⚡ and refuse moves, so a board never bypasses the workflow.
- The ETC panel (ui/etcPanel.tsx) edits only draft Digit Cost Forecast Snapshot lines through documentApi.saveDocument and previews with the same lineEtc / burnDays as the snapshot hook and costPosition (Python twin rules/calc.py), so preview, saved snapshot and server agree.
- Cost screens (budget sheet, remaining rings, EAC equation, 12-period forecast strip, ranked cost codes, K06 cards) read only domain/costScreens.ts over costPosition / subcontract payables and draw with the Enterprise CostKit; use levels come from the budget_warn_pct / budget_over_pct settings (blank = 80 / 100), so every cost screen shows the report's own numbers in one colour rule.
