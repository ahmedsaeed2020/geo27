# DIGIT HR rules
Scope: `src/plugins/digit_hr/`, `src/components/digithr/` and `src/routes/digit-hr.*`.

- HR metrics use `hrMetrics.ts` over the Core metric engine; composite metrics open `/digit-hr/metrics/$metric` with per-source name filters, so count and register populations reconcile.
- Guarded HR decisions live in `operations.ts` and use native workflow/posting plus scoped access; synthetic checks never claim production ACL.
- Contextual drafts pass initial fields to adapter.insert before autonaming, preserving native defaults and atomic employee linkage.
- Payroll/Analytics support routes reuse module workspaces and preserve native details to avoid duplicate state.
- HR identityScope only restricts shared permissions; disabling restores baseline access. Clearance uses native Activity.task links and rollback-safe drafts, never settlement or exit changes.
- HR movements use Core posting/history; pay/company/new-ID require servers.
- Separation handoffs use unfiltered duplicate detection but return existing records only through scoped reads, so hidden records never leak through review controls or cause duplicate drafts.
- HR registers reuse EnterpriseRegister/Core listLayouts with validated user/register URL preferences to avoid duplicate stores.
- HR capture uses Core validation/scoped atomic batches, not posting/device sync; external hooks remain non-transactional.
- HR sections use scoped links/native edits; templates narrow rows; logs never execute; privacy uses scoped overrides and NOT_EVALUATED when unavailable.
- HR navigation (`HrNav`) is a module rail plus a contextual sidebar listing only the shown module's overview, sections and "All"; documents, reports and related pages live inside the section workspace, so no destination depends on a sidebar leaf.
- HR navigation collapse hides only the contextual sidebar (the rail stays), stored as the shared Core module-sidebar user setting (userSettings `module_sidebar`, like DIGIT Pro and the Desk), so narrow screens keep workspace width without changing any destination.
- HR 03.2/03.3 render `WorkforceWorkspace` with a `mode` over one scoped data model; the Experience landing lens resolves URL → per-user saved key (`lensDefault.ts`) → derived default and never widens the offered lenses.
- Submit decisions on DocTypes missing from frozen Core KEEP_STATUS (Shift Request, Interview) validate mandatory fields, submit natively, then restore the decided status; server on_submit effects are never simulated, so the gap stays visible (docs/CORE_GAPS.md).
- HR analytics reconstruct history only from source dates with the registered metric rules, so trends reconcile with KPIs; undated records are counted, never estimated. Sub-period metric drills carry `ret=from~to` so Back restores the originating period.
- `HrOperationalKpi` source definitions are English tooltips only (kept as `data-kpi-source` in Arabic), so technical identifiers never leak into the Arabic interface.
- Employee 360 timeline folds daily records per ISO week via `timelineGroups.ts` (display-only, counts reconcile, search unfolds), so lifecycle events stay visible without hiding any record.
- HR page headers render compact identity + `.dhr-cmdband`; the band remaps HR tokens for content on deep green, so existing controls restyle without per-page overrides or logic changes.
- HR section pages (/hr/<dept>/<section>/<tab>) render exactly three tabs; Overview and department homes come only from product/overview specs (SECTION_SPECS / deptSpec) hosted by OverviewFrame on the Core Dashboard Designer (matrix rows = periods, columns = series; use kit `flip`), and the older Composer layouts (legacy digit-ws:v1 imported read-only) stay for the module control rooms, so every HR figure has one owner and drill.
- HR R9 owner-approved features (APR-01/02, POR-03/04, CAS-04, HIR-04, PAY-04) use the ten archive DocType JSON files in `r9/source` verbatim (converted by `r9/doctypes.ts fromSource`), controller rules as adapter hooks (`r9/hooks.ts`), API rules in `r9/actions.ts` and form panels in `components/digithr/R9Panels.tsx`; DocShare-granted access and the guest `/hr-invite` page stay Frappe-server-only and invites stay off until the owner's site flag, so the preview never claims a server grant or an unapproved policy.

- Saudi payroll numbers (GOSI, EOS, Saudization, preflight, WPS, accruals, lock) are computed only by product/payroll.ts from effective-dated DIGIT HR Policy Settings and written only through product/payrollActions.ts over native Payroll Entry / Salary Slip / Journal Entry posting; a bank IBAN comes from Employee or the latest Applied bank change request (ibanOf), so preflight, WPS file and prints agree.
- The HR manifest keeps report labels in product/reportLabels.ts and registers runners in product/reportsBoot.ts (from boot), because importing the report runner from the manifest creates an adapter init cycle.
- Employee salary / bank fields sit at permission level 1 (manifest property_setters + docperms for HR roles), and HR print templates read rows only through frappe.get_list, so a manager never sees team salary, IBAN or GOSI wage on a form, preview or print.
- HR prints live in product/prints.ts as bilingual Jinja formats on the shared print frame; no template invents a value the record or its linked rows do not hold.
- HR round-2 features live in `r10/` (features/*.ts logic, tools.ts section tools rendered by SectionTools, hooks.ts client rules with hookScripts.ts Python twins, reports in product/reports2.ts), each registered to its HR sections, so every feature has one owner screen and a server twin listed in docs/hr/FRAPPE_DEVELOPER_GUIDE.md.
- Company-less HRMS records (applicants, interviews, feedback, check-ins, grievances) take the company of their linked record (r10/scope.ts linkedCompany via identityScope), and ledgers stay read-only in the HR role matrix, so company isolation holds without new fields and only posting writes ledgers.
- Round-2 deliverables are generated (scripts/hr_round2_dump.ts → hr_round2_result.py → hr_round2_docs.py), so the result CSV, summary and developer guide always match the code.
- The HR band mark sits at the inline end (left in Arabic, right in English) through digit_hr.css only, so the shared band is unchanged for other apps.
- HR visual-round charts live in product/overview/r3charts.ts (R3_EXTRA appended to the section specs) and section hero chips come from SectionSpec.hero (first three ok KPIs otherwise), so each chart and chip reads the same records as the section's KPI cards.
- DEC-015 account need lives in `accountNeedSpec.ts` (Employee field + Python twin, import-free for the manifest) and `userAccounts.ts` (explicit value, else linked/approver/office = Yes, site trade = No); the no-account metric, profile gaps and Employee 360 read only these, and accounts are created only by the explicit «إنشاء حساب» action, so site workers never count as gaps and no account is made automatically.
